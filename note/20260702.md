## 1. 研究问题

前置工作（论文 2510.02679）提出了一个非常好的问题：

> 如何从自然语言（NL）工艺描述中提取出结构化的工艺流程，以约束的形式喂给求解器，自动完成工厂排期并生成可执行的生产计划。

我们在它的基础上提出 FB Pipeline，重新思考"NL → 结构化 → 约束 → 排期 → 生产计划"这条信息流上 LLM 与代码各自该负责的部分。

## 2. 整体信息流 & 与传统/DSL 方法的对比

```
NL 文本 ─► 结构化 JSON ─► 约束矩阵 (or_matrix) ─► 裸排期 ─► 可执行生产计划
```

| 环节 | 传统做法 | DSL 论文做法 | FB Pipeline（本工作） |
|---|---|---|---|
| NL → 结构化 | 人工录入 ERP/APS | DSL 提取 + 翻译 | 纯 LLM 提取 + 多步校验 + 归一化，固定 schema + 额外字段 |
| 结构化 → 约束 | 人工/顾问配置规则 | PDA | linear dependency |
| 约束 → 排期 | 求解器 | 求解器（OR-Tools） | 求解器（OR-Tools，相同） |
| 排期 → 可执行计划 | 人工对照工艺单填工单 | 代码自动回填，从 DSL 程序拿信息 | 代码自动回填，从固定 schema 拿前后产物 / 参数 |

核心判断：环节 3（求解）已经有成熟工具；NL → 结构化信息提取是llm可以充分发挥优势的地方。

## 3. 从 NL 提取结构化语言：需要解决的问题

1. 事实抽取
2. 事实忠实性
3. 格式与语义一致性
4. solver 直接可用（含有关键字段 machine_idx, duration, pre_indexes）
5. solver 结果回填信息生成最终生产方案（根据 job id 和 task id 回填业务字段）

## 4. DSL 方法的局限性

1. 无法处理未知数据
2. 方法比较复杂，需要很长的前驱准备
3. 对不符合规定的数据无法处理，丢失之后影响最终结果，且无法验证
4. 验证方法是字符匹配，JSON 本身的结构化 / DSL 词表限制会让结果虚高
5. 没有和 ground truth 的对比
6. 原文从结构化数据中提取 DSL，存在"鸡生蛋"问题

## 5. 现有 GroudTruth 的其他问题

1. JSP 数据原本是标准的链式结构，被原始 GPT-4o 提取之后，duration / step 都出现了严重错漏

## 6. 我的方法

1. 三步完成信息提取：extract + format + normalize
   - extract：提示词工程对每个 job 进行结构化提取；根据 JSP solver 的信息反推出提取的固定 schema
   - format：对抽取的内容统一格式化，保证提取 key 时的严格字符匹配度，同时减少 normalize 的匹配空间
   - normalize：对同义词的不同表达形式进行归一化，在字符匹配时提高唯一性
2. 添加 verify 步骤，解决提取和 format 的正确性
3. 对提取失败或不合规的 case 标记为 bad case，方便人工介入
4. 优化 evaluation：添加 makespan，评估最终 plan 的实用性；改进 BLEU，更好反映提取信息的正确性
5. 改进构建 JSP route sheet 的部分，让 JSP data → NL → production plan 全链路可验证
6. 可以通过简单的提示词工程更好地适配不同场景

## 7. 核心优势

1. 抛弃 DSL 的复杂流程，不需要预处理数据
2. 处理结构清晰：extract + format + normalize
3. 固定 schema + verify + bad case，解决 LLM 的正确性问题，允许人工介入
4. 更好的评估体系
5. 对模型依赖低，4B 小模型就可以做——LLM 抽取信息并 format 是非常简单的工作
