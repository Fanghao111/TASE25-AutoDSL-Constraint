# 组会汇报笔记 — FB Pipeline（2026-06-22）

## 1. 研究问题

前置工作（论文 2510.02679）提出了一个非常好的问题：

> **如何从自然语言（NL）工艺描述中提取出结构化的工艺流程，以约束的形式喂给求解器，自动完成工厂排期并生成可执行的生产计划。**

我们在它的基础上提出 **FB Pipeline**，重新思考"NL → 结构化 → 约束 → 排期 → 生产计划"这条信息流上 LLM 与代码各自该负责的部分。

### 1.1 本工作的贡献清单（做法 → 意义）

| # | 贡献 | 做法 | 意义 |
|---|---|---|---|
| 1 | **抛弃 DSL 中间桥梁** | NL → 固定 schema JSON，跳过 DSL 设计与翻译 | 回避了 DSL 论文的"鸡生蛋"问题；新工厂/新工艺零成本接入 |
| 2 | **2 阶段 LLM Pipeline + 1 道代码校验**（extract+format 合并 / 事实 verify / 代码 format 兜底 / batch normalize+verify） | per-order: 一次 LLM 调用做 extract+format → 一次 LLM 调用做事实 verify → 一次代码 idempotent format 兜底；batch: 一次 LLM normalize + 一次 diff-based verify | 把"事实正确性 / 格式一致性 / 跨 order 词项一致性"三类问题解耦但合并相关步骤；LLM 调用从最初的 4N+2 降到 2N+2，质量不掉反升 |
| 3 | **代码层 schema validator + bad_case 保留** | 每步 LLM 输出过确定性校验；失败重试 1 次仍失败则打 `bad_case` 继续 | 避开 DSL 那种"校验失败即丢"的纠错盲区，留出人工介入接口 |
| 4 | **跨 order 的全局同义词归一** | Step 3 一次 LLM 调用对所有 order 的 unique values 做聚类映射 | 让约束生成时 component_type 真正可匹配；否则微小命名差异会让前驱依赖全军覆没 |
| 5 | **求解必需字段 / 辅助字段 双轨制** | 固定 schema 拆成参与排期的字段（machine/duration/前后产物）与回填用的字段（component/container/parameters） | 既保证 OR-Tools 输入的简洁可靠，又不丢失工厂可执行所需的语义信息 |
| 6 | **不绕 DSL，直接复用 schema 完成回填** | Step 6 `ground_production_plan()` 把求解器输出的 (start,end,job_id,task_id) 直接缝回同一份 fixed schema 里的 operation / 参数 / 前后产物 | DSL pipeline 也做自动回填，但要先解 DSL 程序里的 `SlotArg/EmitArg`；FB 把这层中间步骤省掉，回填逻辑和提取逻辑共用一套数据结构 |
| 7 | **新增 makespan 评价指标** | 引入 (FB makespan / GT makespan) 比值 | 直接反映"生成的约束有没有把求解器误导成糟糕排期"，比纯 accuracy 更贴近排期质量 |

## 2. 整体信息流 & 与传统/DSL 方法的对比

```
NL 文本 ─► 结构化 JSON ─► 约束矩阵 (or_matrix) ─► 裸排期 ─► 可执行生产计划
```

| 环节 | 传统做法 | DSL 论文做法 | **FB Pipeline（本工作）** |
|---|---|---|---|
| NL → 结构化 | 人工录入 ERP/APS | DSL 提取 + 翻译 | **纯 LLM 提取 + 多步校验 + 归一化** |
| 结构化 → 约束 | 人工/顾问配置规则 | PDA | 关键词全局匹配（默认）/ PDA（备选） |
| 约束 → 排期 | 求解器 | 求解器（OR-Tools） | 求解器（OR-Tools，相同） |
| 排期 → 可执行计划 | 人工对照工艺单填工单 | 代码自动回填（`JSP_result2production_plan()`，从 DSL 程序拿 `SlotArg/EmitArg/parameters`） | **代码自动回填（`ground_production_plan()`，从固定 schema 拿前后产物 / 参数）** |

**核心判断**：环节 3（求解）已经有成熟工具；环节 1/2/4 是 LLM 真正能发挥作用的地方。

## 3. FB Pipeline 当前完整处理流

**输入**：`orders.json`（一个 instance 中每个 order 是一段 NL 工艺描述）
**最终输出**：`SGM_production_plan.json`（可执行生产计划）+ 一整套中间产物（保留可追溯性 / 调试 / 人工修复用）

整个流程分两个阶段：**Step 1–3 是 LLM 阶段**（含 verify，per-order 共 **2 步 LLM 调用** + 1 道纯代码 format 兜底；Step 3 的 normalize+verify 是 batch 级各一次），**Step 4–6 是确定性代码阶段**。

### 3.1 LLM 阶段（per-order: extract+format → factual verify → code format; batch: normalize → verify）

| Step | 输入 | 处理动作 | 产物 |
|---|---|---|---|
| **1. Extract + Format** | `orders.json` | 每个 order 并行调一次 LLM，同时按固定 schema 抽取并套用格式约定（Title Case / PascalCase / lowercase 等） | `step1_extracted.json` |
| **1-verify (factual)** | extract 结果 + 原 NL | LLM 对照原文修正事实性错误（漏步、错机器、错参数等） | `step1_verified.json` |
| **1-format-verify (code)** | factual verify 后的 JSON | 调用 `format_rules.format_data` 用确定性代码做 Title/Pascal/lowercase 兜底——零 LLM 调用，idempotent，把 factual verify 时可能漂掉的格式拉回标准 | `step1_format_fixed.json` |
| **3. Normalize** | 把所有 order 的 machines / operations / component_types / param_keys / param_values 汇总成 5 个集合 | 一次 LLM 调用做**全局**同义词聚类，得到 `{member → canonical}` 映射 | `step3_mappings_pre_verify.json`（pre-verify 中间产物） |
| **3-verify** | **诊断式输入**：每个 category 给 LLM 三样东西——`pre_set`（normalize 前的全量唯一值）/ `post_set`（应用映射后剩下的值）/ `merges`（只列非平凡合并组 `{canonical: [members]}`） | LLM 直接对照这个 diff 检查三件事：(1) over-merging（同组成员是不是真同义）、(2) under-merging（post_set 里还有没有遗漏的同义对）、(3) canonical 选得对不对。返回修正后的 groups；若返回非空且至少含一类 group 就用 verified 版本替换，否则沿用原版 | 应用映射后写出 `step3_normalized.json`、`step3_mappings.json`（均为 post-verify） |

**LLM 阶段的容错机制**（每一步都生效）：
- 每次 LLM 输出先过 `schema_validator.validate_extraction()` 做确定性校验；
- 校验失败先**重试 1 次**；仍失败则把这条记录标为 `{"bad_case": "..."}` 继续往下走，**不删数据**；
- `bad_case` 会一直保留到最终产物里，作为人工介入接口。

### 3.2 代码阶段（Step 4–6，完全确定性，无 LLM）

| Step | 输入 | 处理动作 | 产物 |
|---|---|---|---|
| **4. Build OR Matrix** | step3 normalized | 收集所有 machine 建索引；对每个 step 计算 `(machine_idx, duration_minutes, pre_indexes)`。`pre_indexes` 由 `global_match` 或 `pda` 推导（见第 7 节） | `CGM_or_matrix.json`、`CGM_machines.json` |
| **5. Solve JSP** | OR matrix | 调 OR-Tools 求解器；同时统计 `compile_error_num`（机器索引失败次数）和 `makespan`、`err_rate` | `assigned_jobs.json`、`makespan.txt`、`err_rate.txt` |
| **6. Ground Plan** | `assigned_jobs` + step3 normalized | 把求解器输出的 `(start, end, job_id, task_id)` 重新映射回业务字段：operation、machine、duration、前后产物（component_type）、parameters 全部回填 | `SGM_production_plan.json` |

> Step 6 是"约束抽象 ↔ 可执行计划"的关键桥接：求解器只关心 `(machine, duration, deps)`，但工厂端要看到"几点几分开始什么操作、用什么参数、产出什么"，回填这一步让最终输出真正可执行。

### 3.3 调用入口

`FBPipeline.run()` 中按 `experiment_type` 分三种模式：

- `CPE_CAE_CSE-2`：从 NL 跑完整端到端（Step 1–6）；
- `CSE-1`：跳过 LLM 阶段，直接用 ground truth route sheets 走 Step 4–6（用来单独评估约束生成质量）；
- `SGE`：进一步跳过约束生成，只跑 Step 6 grounding（用来单独评估回填质量）。

这样三个 type 形成**分阶段消融的天然支架**，方便定位误差来源。

### 3.4 端到端最小示例（取自 ta71 / order 0）

**① 输入 NL**（节选第 1、2 步）：

```
The shearing operation uses a Shear (Sheet Metal) machine for 83 minutes
to cut the input sheet metal into sheared sheet metal pieces, employing a
45-degree shear angle, a cutting speed of 100 mm/s, and a straight blade ...
The laser cutting operation on the Laser Cutter takes 70 minutes to further
process the sheared sheet metal into precisely cut sheet metal, using 3000 W
laser power, a cutting speed of 500 mm/min, and nitrogen gas assist ...
```

**② Step 1 抽取（第 1 步的 JSON 片段）**：

```json
{
  "operation": "shearing",
  "machine": "Shear (Sheet Metal)",
  "duration": "83 minutes",
  "precondition":  [{"component_type": "SheetMetal", "container": "conveyor belt", ...}],
  "postcondition": [{"component_type": "SheetMetal", "container": "conveyor belt", ...}],
  "parameters": {"shear angle": "45 degrees", "cutting speed": "100 mm/s", "blade type": "straight"}
}
```

**③ Step 3 归一 → Step 4 OR matrix（order 0 的前 2 行）**：

```
step 0: (machine_idx=18, duration=83,  pre_indexes=[])
step 1: (machine_idx=11, duration=70,  pre_indexes=[0])   ← 关键词匹配出"激光切割依赖剪切产出"
```

`machine_idx=18` → `Sheet Metal Shear`；`machine_idx=11` → `Laser Cutter`。求解器只看 `(machine, duration, deps)` 三元组。

**④ Step 6 回填后的最终生产计划（machine = Sheet Metal Shear 的第 1 个任务）**：

```json
{
  "start": 0, "end": 83, "job_id": 0, "task_id": 0,
  "operation": "Shearing", "machine": "Sheet Metal Shear",
  "duration": "83 minutes",
  "precondition":  ["SheetMetal"],
  "postcondition": ["SheetMetal"],
  "parameters": {"shear angle": "45 degrees", "cutting speed": "100 mm/s", "blade type": "Straight"}
}
```

可以清晰看到：NL 里所有业务字段都被 LLM 抽到 step1；求解器只用了三元组；Step 6 把所有字段重新缝回——执行端拿到这条记录就能直接排工。

## 4. 为什么我们敢"完全基于 LLM"做信息提取

> 现在 LLM 已经足够强，并且**"从 NL 中提取信息并结构化表示"本身是一个相对简单的任务**——它不需要复杂的领域推理，只需要忠实抽取 + 规范表达。

**文献支撑方向**（具体引文需自行核对最新版本）：

- **综述**：Xu et al., *Large Language Models for Generative Information Extraction: A Survey* (arXiv:2312.17617, 2023)——系统梳理 LLM 在 NER / RE / EE 等子任务上接近或超过监督模型的证据。
- **Zero-shot 抽取**：Wei et al., *ChatIE: Zero-Shot Information Extraction via Chatting with ChatGPT* (arXiv:2302.10205, 2023)；Wang et al., *GPT-NER* (arXiv:2304.10428, 2023)——验证仅靠 prompt 即可达到接近 fine-tuned 的水平。
- **Schema-guided / 结构化输出**：Sainz et al., *GoLLIE: Annotation Guidelines improve Zero-Shot IE* (arXiv:2310.03668, 2023)；OpenAI / Anthropic 的 Structured Outputs & Tool Use 文档——证明在给定 schema 时 LLM 输出 JSON 的可靠性已经工程化。
- **领域内应用**：制造/医疗/法律等垂直领域近两年大量 "LLM as extractor" 工作（如 BioGPT, ClinicalIE 等）——说明这条路径在结构化文档抽取上是成熟范式。

**额外内部佐证**：我们 §10.1 计划的"强模型 vs 弱模型"对比，本质就是给这条前提做经验性背书——强模型饱和、弱模型差距明显，正好印证"对强模型这是 easy task"。

因此我们放弃了 DSL 作为中间桥梁，直接让 LLM 输出固定 schema 的 JSON。要解决的问题归纳为两类：

1. **正确性**：关键字、参数、归类（每个字段放进合理的 key）是否正确。
2. **一致性**：由于 NL 的天然不一致，提取后还要保证
   - (a) 同义词归一到统一表达；
   - (b) 大小写、命名格式（PascalCase / Title Case 等）统一。

## 5. 关键设计 1：2-Stage LLM Pipeline + 代码 format 兜底

（具体每一步的输入/动作/产物已在 §3.1 列出，本节只讲设计动机。）

**为什么是"extract+format 合并 + factual verify + 代码 format 兜底"这种拆法？**

第 4 节归纳的两类问题（正确性 / 一致性）本身可以再细分成三件互相独立、但都容易让 LLM 翻车的事：

1. **事实正确性**——和原 NL 比对，有没有漏步、错机器、错参数？只能靠"看原文"修，必须 LLM。
2. **命名格式一致性**——operation 是不是 Title Case、component_type 是不是 PascalCase？规则机械、可枚举，**代码做更可靠且 idempotent**。
3. **跨 order 词项一致性**——单条 order 没问题，但 100 个 order 一汇总出现 `Laser Cutter` / `LaserCutter` / `Laser cutting machine` 三种写法。只能在全局视角下做语义聚类。

→ **任务性质决定承担者**：(1) 必须 LLM；(2) 该交给代码；(3) 必须 LLM 且必须 batch 级。早期版本把 (2) 也用 LLM 做（4N+2 调用），后来验证代码 format 在 ta71 上和 LLM format 持平甚至更稳，于是合并成现在的 2-stage：per-order 只跑 extract+format + factual verify 两次 LLM，再用代码 format 兜一道，最后 batch 级 normalize+verify。

**两项 DSL 论文中没有、但在我们工作里很关键的工程改进**：

1. **代码层 schema validator**（`schema_validator.py`）：每步 LLM 输出先过一道确定性校验，不合规先重试一次，仍不合规则打 `bad_case` 标记继续往下走，**而不是默默丢弃**。
2. **失败信息保留**：所有 `bad_case` 都会原样留在产物里，方便后续人工介入修复，而不是被静默吞掉。

## 6. 关键设计 2：固定 Schema 的取舍

OR-Tools 求解器只需要 `(machine_id, duration, pre_indexes)` 这种结构化输入，所以我们把整个 schema 分成两部分：

- **求解必需字段**（operation、machine、duration、pre/postcondition）：作为固定 schema 的强制项，参与约束生成；
- **辅助字段**（component、container、parameters 等）：不影响排期，但在 `ground_production_plan()` 阶段会被**回填**到最终生产计划里，保证输出是"可执行的工单"，而不是只有时间戳。

这样做的好处：固定 schema 让校验和约束生成都变得简单可靠，同时不损失人类可读性。

## 7. 关键设计 3：约束生成模块

### 7.1 当前实现：keyword global match（默认）

`_derive_precedence_global_match`：
- 对每个 step，扫描它之前的所有 step；
- 如果当前 step 的 `precondition.component_type` 与某个前序 step 的 `postcondition.component_type` 有交集，就建立一条前序依赖。

逻辑非常朴素，但是从 §3.4 的真实例子可以看到：**前驱依赖在我们当前测试集里基本就是线性 / 浅树结构**（一个产物喂给下一个步骤），上下文无关文法的特征几乎用不上。

### 7.2 我的立场（为什么先用 global match）

1. **当前测试集（ta71 类 JSP 任务）case 都比较简单**——每个 order 内步骤之间的依赖几乎都能由"上一步的产出 = 这一步的输入"直接判出来，没有嵌套子流程、没有循环、也没有需要栈式回溯的语义。在这种数据上 global match 的效果已经能跑出 §8 的指标。
2. 所以我**暂不确定这块是否真的需要复杂算法**——这是想和老师确认的核心问题之一。如果未来要扩展到更复杂的工艺（同种产物多实例、嵌套子流程、可重入装配），才有必要换更强的方法。
3. 同时也实现了 **PDA 方案**（`_derive_precedence_pda`）作为备选：用 FIFO 队列维护"已生产产物池"，consume/produce 时增减——可以避免 global match 在"同 component_type 多实例"场景下的过度连边。它和 global match 的对比可以作为消融。

### 7.3 评估：DSL 论文里的 PDA 是从哪借来的？

按我目前理解，**PDA 在制造排期/约束生成领域不是业界通用方案**，更像是该论文作者**从编译原理跨界借用**的——理由：

- 调度/制造工艺领域的"标准"前驱依赖建模方法是 **Petri 网**（MES / 工作流文献的主流）、**DAG / 活动图（PERT/CPM）**、**ECA 规则**这一脉；很少看到把 PDA 当成默认工具。
- PDA 是上下文无关语言识别器，**它真正适合的是嵌套/递归式结构**（典型如带括号匹配的 DSL 句法）。
- DSL 论文作者显然是把自己的 DSL 视作 CFG，所以"DSL 解析 + 约束生成"就自然走 PDA——这是**为了配合 DSL 本身的形式化结构**而引入的工具，并不是因为制造工艺天然就是上下文无关的。

→ 推论：**一旦放弃 DSL 中间层（也就是我们 FB 的设定），就不再有非用 PDA 不可的理由**。剩下的选择应该在「DAG 风格的产物流追踪」这条主干道上比，比如：
- global match（最简单，可能过度连边）；
- 我们的 PDA-FIFO 实现（其实更接近一个产物流"令牌池"，已经偏 Petri 思路了）；
- 完整的 Petri 网 / 显式产物图建模。

> 这块希望在组会上确认两件事：(a) 当前数据复杂度是否值得换更强的算法？(b) 如果要换，是直接做成 Petri 风格、还是保留 PDA 留个对照实验就够？

## 8. 初步结果（ta71，CSE-2）

| 指标 | DSL Pipeline | **FB Pipeline** |
|---|---|---|
| accuracy_rate ↑ | 32.5% | **49.8%** |
| makespan_ratio ↓ | 9.25 | **3.41** |
| runtime_err_rate ↓ | 0.0 | 0.0 |

新增了 **makespan** 作为评价指标——它直接反映"生成的约束有没有把求解器误导成一个很糟糕的排期"。在 ta71 上各项指标都有明显提升。

## 9. 与 DSL 论文的对比 / 我们解决了哪些问题

1. **错误的处理方式不同**
   DSL 在很早期就会基于 DSL 校验丢掉"不合法"的内容，**没有纠错能力**；
   FB Pipeline 把所有失败标注在最终产物中，保留人工修复入口。

2. **DSL 本身存在"鸡生蛋"问题**
   论文里 DSL 是从结构化数据中提取的，又被用来生成结构化数据；
   即便其他工作改成从 NL 提取 DSL，**也只在见过的数据分布上有效，对新工厂/新工艺不通用**。
   我们直接走 NL → 固定 schema，回避了这条链路。

3. **工程可靠性**
   增加了显式校验环节，缓解了 LLM 多次运行的一致性问题。

## 10. 计划继续做的实验（可作为消融 / 补充）

1. **强模型 vs 弱模型**：验证"NL 提取"对 LLM 来说确实是简单任务（强模型饱和，弱模型差距明显）。
2. **校验反馈的作用**：尤其在弱模型上，verify 步骤应能显著提升正确性。
3. **人工修复前 vs 修复后**：证明"保留 bad_case + 提供人工接口"这条路径的价值。
4. **约束生成方案**：global match vs PDA 的对比。
5. **Step 1 架构消融（已落地为 2-stage 默认）**：早期 4-stage 版本（extract → factual verify → LLM format → format verify）现已被 2-stage（extract+format 一次性 + factual verify + 代码 format 兜底）替代——LLM 调用从 4N+2 降到 2N+2，ta71 上 CSE-2 accuracy 反而从 0.556 升到 0.668、makespan 4808→4692。残余可做的消融：(a) 在更大 instance 上复现这个 gap；(b) 验证"代码 format 替代 LLM format"在更脏的真实 NL 上是否仍稳。
6. **完整的 ta71 ~ ta80（10 个 instance × 101 orders）跑通**，让结论更稳。
7. **3-verify 策略消融（部分已实现）**：原方案是"固定取前 3 个 valid order 当上下文"，对全局聚合的映射验证价值有限。**当前实现已经换成诊断式 verify**——每个 category 给 LLM `pre_set / post_set / merges` 三视图，同时检查 over-merging、under-merging、canonical 选择；并落盘 `step3_mappings_pre_verify.json` 作为对照。剩余可做的消融：(a) "无 verify" vs "样本式 verify" vs "诊断式 verify" 三档对比；(b) 在更大的 instance 上看诊断式 verify 是否会因为 pre_set 过大撑爆 context（必要时再设计分类别 / 分批校验）。
